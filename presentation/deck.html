Coverage-guided: цикл обратной связи

Coverage-guided фаззинг: автоматизированное тестирование, при котором инструмент генерирует входы, подает их в цель и сохраняет только те, что открывают новое покрытие: рёбра графа управления потоком. Сбои находятся как аномалии: исключения, нарушения памяти, таймауты.

  • Метки покрытия встраиваются компилятором при сборке; без них фаззер не видит
  • путь выполнения вообще
  • Цель фаззера не доказать корректность программы, а найти несоответствие
  • между тем, как она должна реагировать на вход, и как она на самом деле реагирует

lizard: метрики и отчёт

lizard является статическим анализатором (Python): считает метрики без заголовков, без сборки и без запуска. CCN обозначает число независимых путей в функции: чем выше CCN, тем богаче ландшафт для фаззера. Это эвристический индикатор, а не гарантия.

Выбор: load_env, а не child_process

load_env находится в src/env.c:181, имеет CCN 31 и NLOC 88. Конечный автомат для парсинга строк окружения NAME=VALUE: кавычки, экранирование, таблица состояний (NAMEI ... ERROR).

child_process (CCN 84) слишком рискованен: exec процессов и запись файлов. load_entry уже покрыта референс-обёрткой. parse_args берёт argv, а не байты. edit_cmd работает с файлами crontab и терминалом. main является точкой входа. cron_popen использует popen(), load_user требует парсинга /etc/passwd.

Анатомия обёртки

  • получает сырые байты от фаззера

  • заголовочный комментарий: цель, функция, команды сборки

Принципы 1–4: простота и детерминированность

1. Простота
байты, форма, цель, 0. Никакой инициализации, логирования и собственной обработки ошибок
2. Одна обёртка, одна цель
один fuzz_<функция>.c означает один сценарий или одну функцию
3. Детерминированность
сброс состояния (LineNumber = 0), никаких exit, файлов и сети
4. Проверки до вызова
нулевой или слишком большой вход означает ранний возврат

Каркас обёртки: AFL vs libFuzzer

#ifdef __AFL_FUZZ_TESTCASE_BUF /* AFL: persistent mode через fork-сервер */ int main(void) { __AFL_INIT(); __AFL_FUZZ_INIT(); const unsigned char *data = __AFL_FUZZ_TESTCASE_BUF; while (__AFL_LOOP(10000)) { size_t size = __AFL_FUZZ_TESTCASE_LEN; do_fuzz(data, size); } return 0; } #else /* libFuzzer: главный main генерирует clang'ом */ int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) { do_fuzz(data, size); return 0; } #endif

__AFL_LOOP(10000) является persistent mode: на порядок быстрее, чем перезапуск процесса. Требует детерминированности: нет утечек, нет exit, нет глобального состояния.

Приёмы 1–3: dispatch, fmemopen, структура

Dispatch-байт: первый байт выбирает функцию или режим, остальные являются данными для выбранного режима. В targets/nova/fuzz_libvirt_config.py: data[0] % 5 выбирает один из пяти XML-парсеров libvirt, а data[1:] хранит XML.

fmemopen(): буфер фаззера превращают в FILE*, если цель читает файл. В обёртке load_env: fmemopen(data, size, "r"), после чего цель получает обычный FILE* и не знает, что её фаззят.

Структура: поля извлекаются последовательно, одно за другим, как FuzzedDataProvider в Python, только руками: mode = data[0], n = (data[1] << 8) | data[2], payload = data + 3.

15 / 35

Приёмы 4–5: стабы и include-trick

Стабы: внешние зависимости чужой функции заменяют поддельными реализациями. В fuzz_slirp_input.c весь callback-интерфейс Slirp подменяют стабами; в Python-обёртках это mock.patch. Стаб является самой наивной реальной реализацией, но без побочных эффектов.

Include-trick: статическая функция из чужого файла собирается через подмену main. #define main fuzz_original_main, затем #include "api.c" вместо подключения заголовка #include "api.h".

Разбор образцов: sgetpwent и load_env

Образец sgetpwent из shadow-utils является одной обёрткой, выполненной по правилам «один файл на все фаззеры»: входом служит строка /etc/passwd (name:password:uid:gid:gecos:homedir:shell); нулевые байты заменяются пробелами, потому что passwd не содержит NUL, и тогда фаззер не получит этого диапазона; размер входа ограничен 1024 байтами; применено #undef unused (см. §4.3); защита !defined(__AFL_COMPILER).

Наше решение, fuzz_load_env.c: #define MAIN_PROGRAM делает глобальные cronie доступными в нашей единице трансляции (см. §4.3); fmemopen() превращает буфер в FILE*, поэтому цель получает обычный FILE*; LineNumber = 0 перед каждым входом сбрасывает глобальный счётчик строк; статический буфер envstr выделяется один раз.

Сборка: инструментация и флаги

libFuzzer собирается флагами clang -fsanitize=fuzzer,address -g -O1: -fsanitize=fuzzer встраивает битмап покрытий и главный main, -fsanitize=address включает AddressSanitizer, который находит нарушения памяти, -g даёт отладочную информацию, -O1 является компромиссом между скоростью и стабильностью покрытия. AFL собирается через afl-clang-fast -g -O1 без sanitizer: у него собственный битмап в 64K, fork-сервер и макросы persistent mode.

Сборка: кейс cronie и ошибки

clang -fsanitize=fuzzer,address -g -O1 -DHAVE_CONFIG_H \ -I/opt/fuzzenv/src/cronie-1.5.7/src -I/opt/fuzzenv/src/cronie-1.5.7 \ fuzz_load_env.c /opt/fuzzenv/src/cronie-1.5.7/src/env.c \ /opt/fuzzenv/src/cronie-1.5.7/src/misc.c \ /opt/fuzzenv/src/cronie-1.5.7/src/pw_dup.c -o fuzz_load_env_lf

Пример cronie 1.5.7: берём config.h.manual и cron-paths.h.manual и линкуем только env.c, misc.c и pw_dup.c с обёрткой. Ошибки сборки: undefined reference LineNumber означает, что глобальные cronie не определены в нашей единице трансляции (решается через #define MAIN_PROGRAM); undefined identifier 'unused' означает, что объявлен макрос unused в defines.h shadow (решается через #undef unused перед AFL-веткой).

AFL: команда и элементы

AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1 afl-fuzz -i corpus -o out -V 20 ./fuzz_load_env_afl
  • afl-fuzz: драйвер; мутирует входы и сохраняет новые пути

AFL: метрики и артефакты

Битмап является фиксированным массивом байт. Инструментированная программа, исполняя вход, увеличивает ячейку на каждом ребре графа управления потоком (переход между базовыми блоками): каждому ребру соответствует уникальный индекс, и вход «закрашивает» ячейки на пройденных рёбрах. Измеренный прогон за 20 секунд: execs 1.70M (~85k/s), корпус вырос с 3 до 71, edges 55/331, stability 98.18%, bitmap_cvg 16.62%, saved_crashes 0

Покрытие: Atheris + coverage.py

/opt/atheris/bin/python -m coverage run /opt/atheris/refs/watcher/fuzz_watcher_utils.py \ -atheris_runs=200 -max_len=512 -timeout=5 -detect_leaks=0 corpus /opt/atheris/bin/python -m coverage report /opt/atheris/bin/python -m coverage html /opt/atheris/bin/python -m coverage xml

Отчёт появляется только при штатном завершении fuzzer'а, через -atheris_runs=N, а не через -runs=N. После -runs coverage печатает «No data to report». Пример (200 прогонов): TOTAL 424 stmts, 60 miss, 86%; utils.py 69%, fuzz_watcher_utils.py 85%.

coverage.py замедляет фаззер почти в 2.4 раза (14.3 с против 6.1 с на 500 прогонов), поэтому применяется для визуализации, а не для длительных прогонов.

Atheris: что это

Atheris является обёрткой libFuzzer для Python. Входом являются сырые байты плюс FuzzedDataProvider; главной функцией служит atheris.Setup() с atheris.Fuzz(). Фаззер фиксирует сбой как неперехваченное исключение.

  • Инструментация: байткод при импорте, без компиляции
  • Покрытие строк: coverage.py (см. §8.4)
