## 1. Общая модель

**Определение.** Coverage-guided фаззинг — метод автоматического тестирования,
в котором инструмент генерирует входы, подавая их в целевую функцию, и
сохраняет те входы, которые открывают **новое покрытие** (новые рёбра
графа управления потоком программы). Ошибки находятся как сбои программы:
неперехваченные исключения, нарушения памяти (обнаружимы ASan) или
таймауты.

**Ключевой механизм.** Покрытие доступно только через **инструментацию** —
метки, вставляемые в код **компилятором при сборке**. Собранные из исходников
библиотеки без флагов инструментации фаззер «не видит»: путь выполнения
не отражается. Поэтому фазируемая цель всегда собирается специальным
способом, описанным в разделе 4.

**Три уровня инструментов:**

| Слой | Что делает |
|---|---|
| Компилятор + флаги | Встраивает инструментацию и sanitizer (ASan, UBSan) |
| Обёртка (harness) | Превращает сырые байты фаззера в то, что ожидает цель (файл, структуру) |
| Фаззер (afl-fuzz / libFuzzer / `atheris.Fuzz()`) | Мутирует входы, оценивает покрытие, сохраняет корпус, останавливается на ошибке |

**Что ищет фаззер.** Фаззер не доказывает корректность программы — он ищет
**несоответствие** между тем, как программа должна реагировать на вход, и
тем, как она на самом деле реагирует: утечка памяти, чтение за границей,
неперехваченное исключение, бесконечный цикл, сбой из-за переполненной
структуры. Именно эти нарушения лежат в основе всех последующих разделов.

## 2. Выбор цели: lizard

### 2.1 Зачем метрика сложности

Фаззер тратит время пропорционально числу путей и состояний, которые ему
предстоит исследовать. Цикломатическая сложность (CCN) — количественная оценка числа
линейно независимых путей в функции. Чем выше CCN, тем богаче «ландшафт»
для фаззера: больше ветвей, case-переключений и составных условий, которые
можно открыть мутацией входов.

### 2.2 Что умеет lizard

`lizard` — статический анализатор (Python), способный считать метрики
почти для любого C-подобного или динамического языка **без** заголовков
и зависимости от системы сборки. Для каждого файла выдаёт таблицу
функций:

```
  NLOC    CCN   token  PARAM  length  location
```

| Колонка | Смысл |
|---|---|
| NLOC | Количество непустых строк кода без комментариев |
| **CCN** | Цикломатическая сложность (число линейно независимых путей) |
| token | Количество токенов в теле функции |
| PARAM | Количество параметров |
| length | Размер функции в строках (конец − начало) |
| location | `имя@строки@файл` |

Важно понимать: lizard считает **статическую** сложность — без запуска и
без исполняемого кода. Это эвристический индикатор, а не гарантия; для
выбора таргета его достаточно.

### 2.3 Запуск

```
lizard /opt/fuzzenv/src/cronie-1.5.7/src/*.c
```

Для больших репозиториев полезны фильтры и ключи сортировки:

```
lizard /opt/fuzzenv/src/cronie-1.5.7/src/          # рекурсивный обход
lizard -C 20 /opt/fuzzenv/src/cronie-1.5.7/src/    # предупреждения для функций с CCN > 20
lizard -s cyclomatic_complexity -t 4 ...           # сортировка по CCN, 4 потока
```

Полный список ключей (значения проверены на lizard 1.26.1 в контейнере):

| Ключ | Значение по умолчанию | Что делает |
|---|---|---|
| `-l` | mix (все языки) | выбрать язык/языки анализа (`cpp`, `python`, ...) |
| `-C CCN` | 15 | порог предупреждений: функция с CCN выше порога получит warning |
| `-L LENGTH` | 1000 | порог предупреждений по длине функции, в строках |
| `-a ARGUMENTS` | — | лимит на число параметров (warning выше) |
| `-s FIELD` | — | поле сортировки: `cyclomatic_complexity`, `nloc`, `token_count`, ... |
| `-t THREADS` | 1 | число рабочих потоков |
| `-x PATTERN` | — | исключить файлы, соответствующие `PATTERN` (glob) |
| `-w` | — | только warnings, в формате clang-style (для CI) |
| `--csv`, `--xml`, `--html`, `-H` | — | машиночитаемый/визуальный отчёт вместо таблицы |
| `--compact` | — | не показывать анонимные функции с CCN 1 |

> Сама по себе программа `lizard` ничего не собирает и не запускает — это
> только статический подсчёт. Входа в виде «скомпилированной бинарной цели» у
> неё нет: результат — метрики по каждому файлу.

### 2.5 Критерии выбора цели

CCN — не единственный критерий. Порядок приоритетов:

1. **Вход = сырые байты/строки** (не argv, не сокет, не терминал, не
   поток данных сессии). Фаззеру нужна функция, которая принимает
   что-то, что можно напрямую превратить в байты.
2. **Минимум побочных эффектов.** exec процесса, запись файлов, сеть,
   глобальные переменные, разделяемые с остальным проектом — всё это
   отсекается, так как обёртка должна быть детерминированной и не
   зависить от окружения.
3. **Минимальная линк-зависимость.** Чем меньше .c-файлов нужно, чтобы
   слинковать функцию с обёрткой, тем проще и надёжнее сборка.
4. **Парсинг неструктурированного входа** — типичный источник багов памяти.
5. **Не-дубликат** с уже написанной обёрткой (в референсе `load_entry`
   уже покрыт — повторно фаззить её нет смысла).

### 2.6 Выбор

**`load_env()` (src/env.c:181, CCN 31, NLOC 88)** — конечный автомат для
парсинга строки окружения `NAME=VALUE` с кавычками, экранированием и
таблицей состояний (`NAMEI`, ..., `ERROR`).

Почему не остальные:

- `child_process` (CCN 84) — самый «сложный» кандидат, но exec'ит
  процессы пользователя и пишет в файлы; обёртка пришлось бы маскировать
  exec под стабы — высокий риск бесконечных и недетерминированных вызовов.
- `load_entry` (CCN 67) — уже покрыта референс-обёрткой
  (`fuzz_load_entry.c`); повторный фаззинг не добавляет нового опыта.
- `parse_args` (CCN 54) — аргументы командной строки (argv), а не байты;
  неестественно превратить argv в байтовый поток.
- `edit_cmd` (CCN 52) — оперирует файлами crontab и терминалом.
- `main` (CCN 50) — не функция, а точка входа.
- `cron_popen` (CCN 27) — использует `popen()` и требует стаба системы.
- `load_user` (CCN 25) — требует парсинга `/etc/passwd` (зависимость от
  окружения).

`load_env` — чистый парсер без побочных эффектов, уже линкуется
`misc.c` и `pw_dup.c` вместе с ним (как `load_entry`), и даёт чёткую
демонстрацию приёмов обёрток.

> **Важно.** Выбор — это всегда компромисс между интересностью (CCN),
> достижимостью (побочные эффекты) и воспроизводимостью (минимум
> линк-зависимостей). CCN — только первый фильтр.

## 3. Обёртка (fuzz target)

### 3.1 Анатомия

**Определение.** Обёртка — тонкая программа, которая:
1. получает сырые байты от фаззера;
2. превращает их в то, что ожидает цель (файл, структура, аргументы);
3. вызывает целевую функцию;
4. не накапливает состояние между вызовами.

**Правила (из референс-workspace):**

- **один файл** `fuzz_<функция>.c` на **все фаззеры**;
- **один кодовый путь** на фаззер через `#ifdef __AFL_FUZZ_TESTCASE_BUF`
  (определяется ТОЛЬКО afl-clang-fast);
- **без накапливаемого глобального состояния** между итерациями —
  фаззер считает каждый вход независимым экспериментом;
- заголовочный комментарий — цель, функция, команды сборки.

> Принципы написания обёрток — в §3.2; подробные разборы на образцах —
> в §3.5 и §3.6.

### 3.2 Принципы написания обёрток

Ниже — восемь принципов, которые задают форму любой обёртки (C и Python).
Простые примеры — минимальный код, достаточный для понимания. Подробные
разборы — в §3.5 и §3.6.

#### 3.2.1 Простота: обёртка — точка входа, а не программа

Обёртка умеет ровно то, что нужно для вызова цели: получить байты,
превратить их в форму, ожидаемую целью, вызвать, вернуть 0. Никакой
командной строки, инициализации, логирования, собственной обработки ошибок —
всё это мешает работе фаззера и мешает интерпретации результатов. Минимальная C-обёртка:

```c
#include <stdint.h>
#include <stddef.h>

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    if (size == 0) return 0;
    parse_something(data, size);   /* ровно одна вызовенная цель */
    return 0;                      /* успех — 0 */
}
```

Минимальная Python-обёртка:

```python
import sys
import atheris

with atheris.instrument_imports():
    import my_module   /* цель — импортируется ПОСЛЕ instrument_imports */

def TestOneInput(data: bytes) -> None:
    my_module.parse(data)

atheris.Setup(sys.argv, TestOneInput)
atheris.Fuzz()
```

#### 3.2.2 Одна обёртка — одна цель

Не фаззить два несвязанных модуля в одном таргете. Один `fuzz_<функция>.c`
(или один `fuzz_*.py`) — одна целевая функция или один сценарий, который
можно выразить одной функцией. Если цель — «несколько функций одной
семьи» (например, пять XML-парсеров в libvirt), их объединяют через
dispatch-байт (§3.4, приём (a)) — но это одно решение, зафиксированное в
комментарии. Обёртка описывает **один** путь, а не «все пути».

#### 3.2.3 Детерминированность: сброс состояния между итерациями

Фаззер считает каждый вход независимым экспериментом. Поэтому:

- никакого глобального состояния, которое утекает между вызовами — явный
  сброс перед обработкой или переиспользование статического буфера без
  побочных эффектов;
- никаких `exit()` / `_exit()` внутри цели или обёртки (это завершает
  процесс — для persistent mode это значит разрыв fork-сервера);
- никаких чтений/записей «настоящих» файлов, сетевых вызовов, системных
  зависимостей — если цель их делает, их заменяют стабами (§3.4, приём (d));
- не возвращать «невалидный вход» как ошибку — невалидный вход — это
  обычный путь выполнения, не ошибка обёртки.

```c
static void do_fuzz(const uint8_t *data, size_t size) {
    static char envstr[MAX_ENVSTR + 16];  /* буфер один раз, без аллокаций */
    LineNumber = 0;                       /* сброс глобального счётчика */
    /* ... */
}
```

#### 3.2.4 Проверки до вызова цели: размер и форму входа

Перед вызовом цели обёртка проверяет, что вход вообще годится для цели:
пустой вход, слишком длинный вход, заведомо неинтересная форма. Возврат —
это не ошибка, это нормальный путь (в Python — `return`/`pass`):

```c
static void do_fuzz(const uint8_t *data, size_t size) {
    if (size == 0 || size >= 1024)  /* sgetpwent копит только 1024 байта */
        return;
    /* ... */
}
```

#### 3.2.5 Не перехватывать лишнее

Обёртка перехватывает **только** исключения и коды ошибок, которые цель
документирует как «нормальные» для невалидного входа. Всё остальное должно
всплыть как баг — это и есть то, что ищет фаззер. В C это означает, что
обёртка не маскирует краши цели под «нормальный» путь: нет `exit()` в
обработчике, нет ловушек на parse-ошибках; в Python — явный список ожидаемых
типов исключений:

```python
try:
    StrictDefaultValidatingDraft4Validator(STATIC_SCHEMA).validate(value)
except (watcher_exception.Invalid, jsonschema.ValidationError, ValueError):
    pass   /* документированный отказ — нормальный путь */
# всё остальное — uncaught, пусть падает как баг
```

#### 3.2.6 Формат входа определяется обёрткой

Фаззер не знает никакого формата — он даёт сырые байты. Обёртка сама декодирует
их в структуру: байты как строка (passwd line), байты как файл
(`fmemopen`), байты как структура (ручное слияние или `FuzzedDataProvider`),
байты как сценарий (dispatch-байт). Выбор приёма — за обёрткой, и он
фиксируется в заголовочном комментарии:

```c
FILE *f = fmemopen((void *)data, size, "r");  /* байты → FILE* */
load_env(envstr, f);                           /* цель не знает, что её фаззят */
fclose(f);
```

```python
fdp = atheris.FuzzedDataProvider(data)
mode = fdp.ConsumeIntInRange(0, 5)
raw = fdp.ConsumeBytes(512)
```

#### 3.2.7 Заголовочный комментарий — самообъясняемость

Обёртка должна быть понятна без чата и без README: комментарий сверху
фиксирует цель, функцию, формат входа, команды сборки и сид-набор. Это —
минимальная документация, которую читатель увидит первым (образец —
`fuzz_sgetpwent.c` и `fuzz_load_env.c`).

#### 3.2.8 Python-специфика: порядок импортов

Обёртка для atheris обязана делать две вещи: импортировать цель **после**
`atheris.instrument_imports()` (иначе инструментация не применится) и не
импортировать цель внутри `TestOneInput` (иначе импорт произойдёт на каждой
итерации). Порядок:

```python
import sys
import atheris

with atheris.instrument_imports():
    import jsonschema
    from watcher.common.utils import is_cron_like   # инструментировано

def TestOneInput(data): ...

atheris.Setup(sys.argv, TestOneInput)   # перед Fuzz()
atheris.Fuzz()
```

### 3.3 Общий каркас

```c
#ifdef __AFL_FUZZ_TESTCASE_BUF
/* AFL/AFL++ — persistent mode через fork-сервер */
int main(void)
{
    __AFL_INIT();
    __AFL_FUZZ_INIT();          /* декларации ptr/len + fallback на stdin */
    const unsigned char *data = __AFL_FUZZ_TESTCASE_BUF;
    while (__AFL_LOOP(10000)) {
        size_t size = __AFL_FUZZ_TESTCASE_LEN;
        do_fuzz(data, size);
    }
    return 0;
}
#else
/* libFuzzer — главный main генерирует clang */
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)
{
    do_fuzz(data, size);
    return 0;
}
#endif
```

`__AFL_LOOP(10000)` — persistent mode: процесс не перезапускается между
итерациями (fork-сервер переиспользует процесс). Скорость — на порядок
выше, чем при перезапуске. Требует детерминированности цели: нет утечек,
нет exit, нет глобального состояния.

### 3.4 Приёмы разбора байт-потока

**(a) Dispatch-байт** (dispatch byte). Первый байт потока выбирает функцию
или режим, а остальные байты являются данными для выбранного режима. Пример из
workspace (`targets/nova/fuzz_libvirt_config.py`): выражение `data[0] % 5`
выбирает один из пяти XML-парсеров libvirt, а `data[1:]` содержит XML. Таким
образом несколько функций одной семьи фаззятся одним таргетом.

**(b) Байты как файл — `fmemopen()`.** Если цель читает файл через
`FILE*`, буфер фаззера превращают в обычный файл:

```c
FILE *f = fmemopen(data, size, "r");
load_env(envstr, f);        /* цель не знает, что её фаззят */
fclose(f);
```

Буфер `data` должен жить дольше `FILE*`. Это и есть приём нашей обёртки.

**(c) Байты как структура.** Поля извлекаются последовательно, одно за
другим — ручное разведение, аналог `FuzzedDataProvider` в Python:

```c
int mode = data[0];
uint16_t n = (data[1] << 8) | data[2];
const uint8_t *payload = data + 3;
```

**(d) Стабы.** Внешние зависимости заменяются поддельными реализациями
(в `fuzz_slirp_input.c` весь callback-интерфейс Slirp подменяется стабами;
в Python-обёртках — `mock.patch`). Стаб ведёт себя как «самая наивная»
реальная реализация, но без побочных эффектов.

**(e) Include-trick.** Если цель — статическая функция из чужого файла,
обёртка подставляет заглушку `main`, а затем подключает исходник цели целиком:
`#define main fuzz_original_main` и затем `#include "api.c"` вместо подключения
заголовка `#include "api.h"`. Приём примитивен, но рабочий, когда заголовки
не публикуют API.

### 3.5 Разбор образца: `fuzz_sgetpwent.c` (shadow-utils)

`/opt/fuzzenv/refs/shadow/fuzz_sgetpwent.c` — единственная обёртка
workspace, выполненная по правилам «один файл на все фаззеры».

Разбор по блокам:

1. **Заголовочный комментарий** — что фаззится (`sgetpwent`), команды сборки,
   формат входа (строка `/etc/passwd`: `name:password:uid:gid:gecos:homedir:shell`).
2. **AFL-ветка:** `#undef unused` (см. §4.3),
   `__AFL_FUZZ_INIT()`, `__AFL_INIT()`, `while (__AFL_LOOP(10000))`.
3. **libFuzzer-ветка:** `LLVMFuzzerTestOneInput`.
4. **Общая `do_fuzz()`:** ноль-байты заменяются пробелами (строка passwd
   не содержит NUL — фаззеру «запрещаем» этот диапазон), ограничение
   `size < 1024`.
5. **Защита от ложного определения `__AFL_FUZZ_TESTCASE_BUF`** — проверка
   `!defined(__AFL_COMPILER)`, т.е. что макрос определил AFL, а не кто-то
   другой (config.h shadow может определить его случайно).

### 3.6 Разбор нашего решения: `fuzz_load_env.c`

Полный код обёртки — в `exercises/full-cycle/solution/fuzz_load_env.c`
(не читайте до завершения задания). Ключевые решения:

- `#define MAIN_PROGRAM` — глобальные cronie определяются в нашей TU
  (см. §4.3);
- `fmemopen()` — цель получает «обычный» `FILE*`, не зная, что её фаззят;
- `LineNumber = 0` перед каждым входом — сброс глобального счётчика строк
  cronie (иначе состояние утекает между итерациями);
- `static char envstr[MAX_ENVSTR + 16]` — буфер, выделяемый один раз.

## 4. Сборка

### 4.1 Модель инструментации

**libFuzzer.** Любой clang с флагами:

```
clang -fsanitize=fuzzer,address -g -O1 <файлы> -o fuzz_target
```

- `-fsanitize=fuzzer` — встраивает битмап покрытий **и** главный `main`
  (таргет = `LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)`);
- `-fsanitize=address` — AddressSanitizer: ловит нарушения памяти
  (heap-overflow, use-after-free, double-free) — это и есть «сбой»,
  который мы ищем;
- `-g` — символы для читаемых отчётов ASan;
- `-O1` — оптимизация: `-O0` на порядки медленнее, `-O2/-O3` искажают
  стабильность покрытий (оптимизатор удаляет «мёртвый» код). `-O1` —
  стандартный компромисс для фаззинга.

**AFL.** Собственный компилятор-обёртка `afl-clang-fast`:

```
afl-clang-fast -g -O1 <файлы> -o fuzz_target
```

Тот же clang, но afl-обёртка: своя битмап покрытий (64K, 2^16 байт), persistent-mode макросы,
fork-сервер. Битмапы AFL и libFuzzer **несовместимы** — под каждый фаззер
своя сборка одного и того же кода.

### 4.2 Кейс cronie: сборка без autotools

Cronie 1.5.7 — проект на autotools. Но нам нужен **только парсер**, а не демон
с PAM/selinux/inotify. Поэтому в референсе
(`/opt/fuzzenv/refs/cronie/`) лежат два файла:

- `config.h.manual` — конфигурация «от руки» (то, что бы сгенерировал `./configure`);
- `cron-paths.h.manual` — пути, генерируемые `make`.

Сборка (libFuzzer):

```
cp /opt/fuzzenv/refs/cronie/config.h.manual      /opt/fuzzenv/src/cronie-1.5.7/config.h
cp /opt/fuzzenv/refs/cronie/cron-paths.h.manual  /opt/fuzzenv/src/cronie-1.5.7/src/cron-paths.h

clang -fsanitize=fuzzer,address -g -O1 -DHAVE_CONFIG_H \
  -I/opt/fuzzenv/src/cronie-1.5.7/src -I/opt/fuzzenv/src/cronie-1.5.7 \
  fuzz_load_env.c \
  /opt/fuzzenv/src/cronie-1.5.7/src/env.c \
  /opt/fuzzenv/src/cronie-1.5.7/src/misc.c \
  /opt/fuzzenv/src/cronie-1.5.7/src/pw_dup.c \
  -o fuzz_load_env_lf
```

Сборка (AFL): та же команда с `afl-clang-fast` и без `-fsanitize=address`.

| Флаг clang/afl-clang-fast | Значение/назначение |
|---|---|
| `-fsanitize=fuzzer` | встроить цикл фаззинга libFuzzer (главный `main` и битмап покрытий) — нужен только для libFuzzer-сборки |
| `-fsanitize=address` | встроить AddressSanitizer: нарушения памяти (overflow, use-after-free, double-free) — это «сбой», который ищет фаззер |
| `-g` | отладочная информация — ASan/libFuzzer печатают читаемые отчёты (функции, строки) вместо адресов |
| `-O1` | оптимизация уровня 1: `-O0` — на порядки медленнее; `-O2/-O3` агрессивно удаляют «мёртвый» код и искажают покрытие |
| `-DHAVE_CONFIG_H` | определить макрос `HAVE_CONFIG_H` — cronie через `config.h` решает, что включать при сборке |
| `-I<dir>` | добавить каталог в поиск заголовков (без него — `undefined reference` на внутренние .h). Можно указывать несколько |
| `-o <имя>` | имя выходного бинарника |

Обратите внимание: линкуем **не всю программу**, а только .c-файлы, необходимые для
линковки целевой функции. Фаззим функцию, а не демон.

### 4.3 Таблица ошибок и решений

| Симптом | Причина | Решение |
|---|---|---|
| `undefined reference to LineNumber` (cronie) | глобальные cronie определены только в main-файлах (`#define MAIN_PROGRAM`) | `#define MAIN_PROGRAM` в обёртке до `#include "globals.h"` — тогда globals.h определяет глобальные в нашей TU |
| `use of undeclared identifier 'unused'` (shadow + AFL) | `defines.h` shadow определяет макрос `unused`, ломающий `__attribute__((used,unused))` внутри `__AFL_INIT()` в C-режиме clang | `#undef unused` перед AFL-веткой |
| `undefined: __afl_persistent_loop` / битмап-ссылки | собираешь AFL-сборку обычным clang (или наоборот) | каждая сборка — своим компилятором; не смешивать объекты |
| рантайм libFuzzer не найден | в Debian рантайм libFuzzer в пакете `libclang-rt-14-dev` (секция **contrib**) | включить contrib в sources (в нашем образе уже включён) |
| `use of undeclared identifier` на «чужих» заголовках | проекту нужен `config.h` от `./configure`, которого нет | config «от руки» (`config.h.manual`) или запуск `./configure` с минимумом флагов |
| компилятор «падает» на `-O2` с ASan | известная проблема ASan при оптимизации | оставить `-O1` |
| `No rule to make target 'all'` | нет Makefile/autotools | читать `configure.ac`/`Makefile.am`, собирать нужную цель вручную |

Главный принцип: **собирай минимум файлов, достаточный для линковки целевой
функции**. Всё остальное — демон, сеть, права — в фаззинг не тянем.

## 6. Прогон AFL

### 6.1 Команда

```
mkdir -p corpus
cp /opt/course/exercises/full-cycle/seed/*.cr corpus/
# в контейнере:
AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1 afl-fuzz -i corpus -o out -V 20 ./fuzz_load_env_afl
```

Разбор строки команды, элемент за элементом:

| Элемент | Значение |
|---|---|
| `AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1` | переменная окружения перед командой — см. ниже |
| `afl-fuzz` | драйвер AFL++: читает сиды из `-i`, мутирует входы, сохраняет те, что открывают новое покрытие |
| `-i corpus` | входная папка с стартовым корпусом (обязательный флаг). Сюда попадает `corpus/` со сидами |
| `-o out` | выходная папка для результатов (обязательный флаг). В ней: `out/default/queue/` (найденный корпус), `out/default/crashes/`, `out/default/hangs/`, `out/default/fuzzer_stats`, `out/default/plot_data` |
| `-V 20` | «fuzz for a specified time then terminate» — время фаззинга 20 секунд, после чего программа сама остановится. Без флага — цикл до Ctrl-C |
| `./fuzz_load_env_afl` | позиционный аргумент: бинарник, который фаззят (без аргументов — ничего не передаём) |

Полезные ключи, которые можно добавить: `-t msec` (таймаут на один вход,
по умолчанию автоматический подбор (~1000 мс); `+` после значения — пересчитать
таймаут автоматически), `-m megs` (лимит памяти на child process, 0 — без
ограничений), `-D` (deterministic mode, один раз на каждую queue-запись),
`-p schedule` (power schedule: `fast` по умолчанию, `explore`, `exploit`,
`seek`, `rare`, `mmopt`, `coe`, `lin`, `quad`), `-E execs` (остановиться
после приблизительно N прогонов), `-s seed` (фиксированный сид RNG — для
воспроизводимости), `-x file` (словарь; можно указать до четырёх),
`-g min` / `-G max` (минимум/максимум длины генерируемого входа, по умолчанию
1/1048576 байт).

### 6.1.1 Переменная окружения `AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1`

При запуске `afl-fuzz` читает системный файл `/proc/sys/kernel/core_pattern`.
Он определяет, куда ядро шлёт уведомление о краше. Проверка выполняется в
`check_crash_handling()` (`src/afl-fuzz-init.c`). В нашем контейнере в файле
стоит:

```
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h %d %F
```

то есть уведомление о краше уходит **через пайп во внешнюю утилиту**
(`systemd-coredump`). Внешний обработчик задерживает доставку уведомления в
фаззер через `waitpid()`, из-за чего сбой может быть ошибочно классифицирован
как таймаут (`program timeout`).

**Без переменной окружения `afl-fuzz` не стартует вовсе** — падает с
`[-] PROGRAM ABORT : Pipe at the beginning of 'core_pattern'`.

Официальный способ решения (из самого сообщения): войти под root и выполнить
`echo core >/proc/sys/kernel/core_pattern`. В контейнере это невозможно —
`/proc` доступен только для чтения (проверено: `Read-only file system`).

`AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1` — единственная доступная здесь
альтернатива: она подразумевает «мы согласны с задержкой доставки уведомлений
о сбое» и отключает проверку-забастовку. Это не «улучшение» фаззинга —
прогон останавливается без неё, с ней — продолжается, с осознанным ограничением
окружения. Именно поэтому она есть в команде выше.

> Важно: если бы у нас был root и возможность править `/proc/sys/kernel/core_pattern`
> (например, на хосте или в privileged-контейнере), это был бы более чистый
> подход — ядро будет печатать core-дамп прямо в файл, без внешней утилиты.

### 6.2 Полная картина на экране

AFL++ выводит статус каждые 30–60 секунд; на выходе отображаются
`execs/s`, `cycles done`, число файлов в корпусе и их favored-часть,
стабильность и доля закрашенной битмапы. Точный формат зависит от версии;
фрагмент реального прогона 20 секунд:

```
cycles_done   : 35
execs_done    : 1 699 967
execs_per_sec : 84 940
corpus_count  : 71
corpus_favored: 9
stability     : 98.18%
bitmap_cvg    : 16.62%
edges_found   : 55  (из total_edges = 331)
max_depth     : 3
saved_crashes : 0
saved_hangs   : 0
```

### 6.3 Смысл метрик

| Метка | Смысл |
|---|---|
| `time` | Время работы |
| `execs_done` | Всего выполненных входов |
| `corpus (favored)` | Счётчик корпуса (число входов / из них избранных) |
| `stability` | Доля входов, выполнение которых детерминировано; <99% — недетерминизм (таймеры, аллокации) |
| `edges_found` | Открытые рёбра битмапа (мера покрытия) |
| `bitmap_cvg` | Доля закрашенной битмапы (0–100%) |
| `saved crashes` | Количество сохранённых аварийных входов |
| `last find` | Время последнего нового корпуса |
| `cycle done` | Полный проход по очереди (корпус = путь выполнения) |

### 6.4 Артефакты

Выходная папка `out/`:

| Файл | Что это |
|---|---|
| `out/default/queue/` | корпус (файлы-входы, упорядоченные по depth) |
| `out/default/crashes/` | аварийные входы |
| `out/default/hangs/` | входы, вызвавшие таймаут |
| `out/default/fuzzer_stats` | машинная статистика |
| `out/default/plot_data` | тайм-серия (cycles, execs/s, corpus) |

Проверка (фрагмент реального прогона):

```
$ grep -E "execs_done|edges_found|stability" out/default/fuzzer_stats
execs_done        : 1698967
edges_found       : 55
stability         : 98.18%
```

### 6.5 Что делать с `stability < 99%`

Стабильность ниже 99% означает, что повторные запуски одного и того же
входа дают разные битмапы. Возможные причины: вызовы системных таймеров,
`rand()`, аллокации, чьи адреса влияют на поведение, — или persistent mode
с частично не сброшенным состоянием обёртки. Для парсеров это редкость.

Порядок действий:

1. Проверить, что обёртка сбрасывает состояние (в примере — `LineNumber = 0`
   перед каждым входом), а persistent mode не скрывает утечек памяти.
2. Проверить код цели на вызовы системных функций, чьи результаты
   меняются между запусками (`time()`, `getpid()`, `rand()`).
3. Если stability стабильно <99% — временно отключить persistent mode
   (`__AFL_LOOP(10000)` → `__AFL_LOOP(1)`, или переменная окружения
   `AFL_NO_FORKSRV=1`) и сравнить.
4. Переменная `AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1` — это про подавление
   проверки `core_pattern` на старте (см. §6.1.1), а **не** про stability.
   Она не помогает с stability вообще.

## 7. Прогон libFuzzer

### 7.1 Команда

```
./fuzz_load_env_lf corpus/ -max_len=4096 -runs=200000 -print_final_stats
```

| Элемент | Значение по умолчанию | Что делает |
|---|---|---|
| `corpus/` | — | позиционный аргумент: каталог с валидными входами. Позволяет fuzzer'у начать с валидной базы |
| `-max_len=4096` | 0 (тогда libFuzzer угадывает по корпусу) | максимальная длина выхода, байты |
| `-runs=200000` | `-1` (бесконечно) | число прогонов, после которого прогон останавливается. Без флага — бесконечный цикл |
| `-print_final_stats` | 0 | «If 1, print statistics at exit» — итоговая строка `DONE ...` |
| `-help=1` | 0 | «Print help» — полный список флагов. **Важно:** `-help` (без `=1`) НЕ валиден и печатает «unrecognized flag», затем продолжает фаззить (и никогда не остановится) |
| `-seed=N` | 0 (случайно) | фиксированный сид RNG — для воспроизводимости |
| `-timeout=N` | 1200 | секунд на один вход; длиннее — считается timeout и процесс абортится |
| `-max_total_time=N` | 0 | максимальная общая длина fuzzing, секунд |
| `-merge=1` | 0 | объединить 2-е и последующие корпуса в 1-й (минимизация корпуса) |
| `-dict=file` | 0 | экспериментальный: использовать файл-словарь для мутаций |
| `-only_ascii=1` | 0 | генерировать только ASCII-входы |
| `-fork=N` | 0 | экспериментальный: fuzzing в подпроцессе |

> Заметка: флаги libFuzzer — это **не** те же ключи, что у AFL++
> (`-i`, `-o`, `-V`) или у atheris (`-max_len`, `-timeout`, `-runs`).
> Имена совпадают частично, семантика различается — не путать.


| Метка | Смысл |
|---|---|
| `cov` | Число покрытых блоков/путей (близко к «coverage») |
| `ft` | Число «новых точек» (новые пути/features) |
| `corp` | Размер корпуса (число файлов / байт) |
| `lim` | Текущий лимит размера входа (автоматически увеличивается) |
| `exec/s` | Скорость (в этот момент `0` — прогон завершён) |

После остановки libFuzzer печатает **recommended dictionary** — токены,
которые чаще встречались в новых путях. Это аналог автоматически генерируемого словаря у AFL.

### 7.3 Сравнение

| | AFL | libFuzzer | Atheris |
|---|---|---|---|
| Сборка | `afl-clang-fast` | `clang -fsanitize=fuzzer,address` | нет — байткод-инструментация при импорте |
| Запуск | `afl-fuzz -i corpus -o out ./bin` | `./bin corpus/ -max_len=...` | `python fuzzer.py corpus/ -runs=...` |
| Persistent mode | `__AFL_LOOP` в обёртке | встроен (main генерирует clang) | встроен (Setup + Fuzz) |
| Покрытие | edges / bitmap_cvg / stability | cov / ft / lim | `cov`/`ft`/`corp`/`lim` из статуса + coverage.py (§8.4) |
| Артефакты | `fuzzer_stats`, `plot_data`, `queue/` | stdout + recommended dictionary | stdout + recommended dictionary |
| Корпус | `out/queue/` | `corpus/` (на месте) | `corpus/` (на месте) |
| Покрытие строк | — | llvm-cov (§8.3) | coverage.py (§8.4) |

Практический вывод: **одна обёртка — два фаззера**. Запускать оба:
они находят разные вещи (у AFL сильнее havoc-мутации, у libFuzzer —
dictionary/crossover и проще автоматизация через CI).

## 8. Сборка покрытия

### 8.1 Что считать покрытием

Покрытие — доля **исполненных** элементов кода (строки, регионы, функции,
ветви) при заданном наборе входов. Для фаззера это и есть цель, которую
мы измеряем после прогона.

### 8.2 AFL: edges из статистики

AFL сохраняет в `fuzzer_stats`:

```
edges_found       : 55
total_edges       : 331
bitmap_cvg        : 16.62%
```

Это мера покрытия **путей выполнения**. Для глубжего анализа:

- `afl-whatsup` — мониторинг активных запусков;
- `afl-cmin` — минимизация корпуса (сохранить только входы, покрывающие
  новые пути): `afl-cmin -i corpus_in -o corpus_out -- ./fuzz_target @@`;
- `afl-plot` — график (требует gnuplot).

### 8.3 libFuzzer: `-print_final_stats` и llvm-cov

**Быстрый путь** (после прогона):

```
./fuzz_load_env_lf corpus/ -max_len=4096 -runs=100000 -print_final_stats
```

Итоговая строка: `DONE cov: 47 ft: 164 corp: 77/2080b lim: 1788`.

**Полный путь (line-level coverage)** — сборка со строками покрытия
и отчёт через LLVM. Команды воспроизводимы в чистом образе (проверено):

```
# 1. Подготовить рабочую папку (копия обёртки и корпуса)
SRC=/opt/fuzzenv/src/cronie-1.5.7
mkdir -p /tmp/cov_out && cd /tmp/cov_out
cp /opt/course/exercises/full-cycle/solution/fuzz_load_env.c .
mkdir -p cov_corpus && cp /opt/course/exercises/full-cycle/seed/*.cr cov_corpus/

# 2. Пересобрать с флагами coverage mapping
clang -fprofile-instr-generate -fcoverage-mapping \
  -fsanitize=fuzzer,address -g -O1 -DHAVE_CONFIG_H \
  -I$SRC/src -I$SRC \
  fuzz_load_env.c $SRC/src/env.c $SRC/src/misc.c $SRC/src/pw_dup.c \
  -o cov_lf

# 3. Прогон на корпусе (profraw сохраняется в текущую папку)
./cov_lf cov_corpus -runs=3000

# 4. Сборка профиля
llvm-profdata merge -sparse default.profraw -o default.profdata

# 5. Отчёты
llvm-cov report ./cov_lf -instr-profile=default.profdata
llvm-cov show   ./cov_lf -instr-profile=default.profdata  # line-level с счётчиками
```

| Команда/флаг | Пояснение |
|---|---|
| `clang -fprofile-instr-generate` | встроить счётчики профиля: каждый запуск пишет `default.profraw` |
| `clang -fcoverage-mapping` | встроить coverage-mapping, который `llvm-cov` использует для привязки покрытия к строкам исходника |
| `./cov_lf` (с `-runs=3000`) | тот же флаг `-runs`, что разобран в §7.1 |
| `llvm-profdata merge -sparse default.profraw -o default.profdata` | `merge` — объединить profraw-файлы; `-sparse` — компактный формат; `-o` — имя выходного файла |
| `llvm-cov report ./cov_lf -instr-profile=default.profdata` | `report` — сводная таблица по файлам; `./cov_lf` — бинарник (llvm-cov читает отладочную информацию, чтобы привязать счётчики к исходнику); `-instr-profile` — путь к profdata |
| `llvm-cov show   ./cov_lf -instr-profile=...` | line-level вывод: каждая строка исходника с счётчиками исполнения |

Пример (проверено):

```
TOTAL    465 regions  19.78%   |  30 functions  16.67%
         582 lines    20.10%   |  322 branches 20.81%
env.c    156 regions  45.51%   |  209 lines   40.19%
fuzz_load_env.c 8 regions 87.50%  |  15 lines   93.33%
```

Вывод: обёртка хорошо покрыта (93% строк), целевая логика (`env.c`) —
нет (40%). Это и есть главный сигнал, почему фаззинг продолжается:
корпус должен расти до тех пор, пока покрытие растёт.

### 8.4 Atheris: сборка покрытия через coverage.py

Внутренняя метрика fuzzer'а (`cov` из строки `DONE`, см. §9) — это
**битмап-покрытие** (число «путей», открываемых корпусом), по смыслу
близкое к `edges_found` у AFL. Но для line-level покрытия atheris
официально поддерживает `coverage.py` — тот же инструмент, что и для обычных
тестов на Python (README atheris, раздел «Visualizing Python code coverage»).
В образе fuzz-py он уже установлен (`coverage==7.6.10`).

Цепочка команд:

```
# 1. Подготовить рабочую папку с сид-корпусом (как в демо — 5-полевой cron)
cd /tmp/covtest && mkdir -p corpus && printf "* * * * *\necho hi\n" > corpus/seed1
/opt/atheris/bin/python -m coverage run /opt/atheris/refs/watcher/fuzz_watcher_utils.py \
    -atheris_runs=200 -max_len=512 -timeout=5 -detect_leaks=0 corpus

# 2. Отчёт
/opt/atheris/bin/python -m coverage report        # текстовая таблица в терминале
/opt/atheris/bin/python -m coverage html           # интерактивный HTML в htmlcov/
/opt/atheris/bin/python -m coverage xml            # машинночитаемый XML для CI
```

| Элемент | Значение |
|---|---|
| `python -m coverage run` | запуск программы под coverage.py; coverage пишет `.coverage` в текущую папку |
| `-atheris_runs=200` | число прогонов, после которого fuzzer **штатно** завершается и записывает отчёт (это собственный флаг atheris — см. ниже) |
| `-max_len=512 -timeout=5 -detect_leaks=0` | те же флаги, что и в §9.4 (те же самые, не новые) |
| corpus (`corpus`) | позиционный аргумент — каталог с сид-входами |
| `coverage report` | таблица «файл / строки / пропуски / процент» по текущим `.py` в репозитории |
| `coverage html` / `coverage xml` | те же данные в интерактивном HTML или машинном XML |

Пример (проверено, 200 прогонов):

```
Name                                                 Stmts   Miss  Cover
--------------------------------------------------------------------------
/opt/atheris-src/watcher/watcher/__init__.py               4      0   100%
/opt/atheris-src/watcher/watcher/_i18n.py                 11      2    82%
/opt/atheris-src/watcher/watcher/common/exception.py     261     25    90%
/opt/atheris-src/watcher/watcher/common/utils.py          64     20    69%
/opt/atheris/refs/watcher/fuzz_watcher_utils.py           84     13    85%
--------------------------------------------------------------------------
TOTAL                                                    424     60    86%
```

> **Важно.** Отчёт генерируется **только при штатном завершении** fuzzer'а:
> по флагу `-atheris_runs=N` (или по исключению/`sys.exit()`). Если
> завершить прогон через libFuzzer-флаг `-runs=N` — **отчёт не появится**
> (проверено: `coverage report` после `-runs=200` печатает «No data to report»).
> Именно поэтому в примере ниже использован `-atheris_runs`.
>
> coverage.py заметно замедляет fuzzer (измерено: ~14.3 с против ~6.1 с на
> 500 прогонов, примерно в 2.4 раза). Используйте её для визуализации и для
> контрольных снимков, а не для длительных прогонов.


## 9. Atheris (Python)

### 9.1 Кратко: что это и чем отличается

Atheris — обёртка над libFuzzer для Python. Отличия от C-фаззинга:

| | C (libFuzzer / AFL) | Python (Atheris) |
|---|---|---|
| Инструментация | Компиляторная (битмап в бинарнике) | Байткод-инструментация при импорте |
| Вход | Сырые байты | Сырые байты + `FuzzedDataProvider` |
| Крах | Сигнал / ASan / ошибка | Неперехваченное исключение |
| `main` | Генерирует clang'ом | `atheris.Setup()` + `atheris.Fuzz()` |
| Покрытие строк | llvm-cov (§8.3) | coverage.py (§8.4) |

### 9.2 Структура обёртки

```python
import sys
import atheris

with atheris.instrument_imports():          # импорты — внутри блока, иначе нет покрытия
    from my_target_module import target_function

def TestOneInput(data: bytes) -> None:
    fdp = atheris.FuzzedDataProvider(data)
    mode = fdp.ConsumeIntInRange(0, 5)     # dispatch: режим входа
    if mode == 0:
        target_function(fdp.ConsumeUnicode())
    elif mode == 1:
        target_function(fdp.ConsumeUnicodeNoSurrogates(64))
    ...

atheris.Setup(sys.argv, TestOneInput)
atheris.Fuzz()
```

### 9.3 `FuzzedDataProvider` — разбор байт-потока в структуру

| Метод | Что возвращает |
|---|---|
| `ConsumeBytes(count)` | bytes фиксированной длины |
| `ConsumeString(count)` | str, может содержать surrogates |
| `ConsumeUnicode(count)` | str, может содержать surrogates |
| `ConsumeUnicodeNoSurrogates(count)` | str без surrogates |
| `ConsumeInt(nbytes)` | signed int |
| `ConsumeUInt(nbytes)` | unsigned int |
| `ConsumeIntInRange(min, max)` | int в диапазоне |
| `ConsumeFloat()` | float |
| `ConsumeBool()` | bool |
| `ConsumeIntList(count, nbytes)` | список int |
| `PickValueInList(lst)` | случайный элемент списка |
| `fdp.remaining_bytes` | остаток байт (свойство, не метод) |

> Методы выше — фиксация в версии atheris 3.0.0, установленной в образе;
> список полных методов — `dir(atheris.FuzzedDataProvider(b""))`.

Правило фиксированного порядка: вызовы `Consume*` должны идти в том же
порядке на каждой итерации, иначе покрытие невоспроизводимо.

### 9.4 Демо: watcher

В `/opt/atheris/refs/watcher/fuzz_watcher_utils.py` — обёртка для
`watcher.utils.*` (cron-parser). Запуск из каталога исходников watcher
(так же, как в дымовом тесте образа):

```
cd /opt/atheris-src/watcher
/opt/atheris/bin/python /opt/atheris/refs/watcher/fuzz_watcher_utils.py \
    -max_len=512 -timeout=5 -detect_leaks=0 -runs=10000 /tmp/wcorpus
```

> Выбор Python-цели выполняется **тем же lizard** (см. §2.3.1) — та же
> команда, те же ключи, та же таблица `NLOC / CCN`.

> Импорт `watcher` работает и из любого другого каталога — в образе он
> установлен editable (.pth-файл), импорт не зависит от текущей директории.
> Каталог watcher нужен здесь как образец, как и в дымовом тесте образа;
> `watcher/__init__.py` вызывает `pbr.version.VersionInfo('python-watcher')`,
> но в этом образе версия разрешается в `0.0.0` и не зависит от cwd
> (проверено: `0.0.0` из `/tmp`, из репо и из `/opt/atheris`).

| Элемент | Значение |
|---|---|
| `/opt/atheris/bin/python` | python-интерпретатор из venv с atheris (не системный) |
| `fuzz_watcher_utils.py` | точка входа: `Setup(argv, TestOneInput)` + `Fuzz()` |
| `-max_len=512` | максимальная длина входа, байты (те же семантики, что у libFuzzer) |
| `-timeout=5` | секунд на один вход; вход, выполняющийся дольше, — timeout (по умолчанию 1200) |
| `-detect_leaks=0` | выключить leak-detection (по умолчанию 1 при включённом LeakSanitizer) |
| `-runs=10000` | стоп после 10000 прогонов (по умолчанию — бесконечно) |
| `/tmp/wcorpus` | каталог с валидным входом |

Проверено (10k runs):

```
#10000	DONE   cov: 262 ft: 756 corp: 29/210b lim: 34
```

Line-level покрытие для atheris — отдельная цепочка coverage.py, см. §8.4
(важно: прогон должен завершиться по `-atheris_runs`, а не по `-runs`).

### 9.5 Замечания

- Из 10 Python-обёрток workspace **не все поднимаются**: `glance.common.json_utils`
  не существует в релизах glance; `cinder.api.common` тянет keystoneclient,
  удалённый с PyPI. Проверяйте `python -c "import <модуль>"` **до** запуска фаззера.
- **instrument_imports() до импорта** — без этого покрытие не появится.
- **Не импортируйте цель внутри `TestOneInput`** — иначе импорт повторяется
  на каждой итерации (медленнее и не покрывается).
- **Не ловите все исключения** — только документированные (`ValueError`,
  `TypeError`...); всё остальное — баг.
- **Избегайте недетерминизма** — `random`, `time.now()`, `os.urandom()`
  внутри `TestOneInput`.

## 10. Jazzer и Go

### 10.1 Jazzer (JVM)

Coverage-guided фаззер для JVM, построенный на libFuzzer (bytecode
instrumentation во время загрузки классов). В workspace —
`targets/spring_security/run-springdoc-fuzzer.py` — тест для FuzzSpringdoc.

Базовый сценарий:
1. Реализовать `fuzzerTestOneInput(byte[])` (или `(FuzzedDataProvider)`).
2. Собрать JAR с таргетом.
3. Запустить:
   ```
   java -cp <classpath>;jazzer.jar com.code_intelligence.jazzer.Jazzer \
       --target_class=<fuzz-class> [corpus_dir]
   ```
4. Артефакты: `crash-<sha1>` (вход), `Crash-<sha1>.java` (репродукция).

Отличия: JVM-исполнение (JIT, GC), сборка JAR'ов, нет ASan — сбои
фиксируются uncaught exceptions и sanitizers JVM.

### 10.2 Go

Coverage-guided фаззинг **встроен в stdlib** (`testing`) с Go 1.18.

```go
func FuzzAddPort(f *testing.F) {

        // логика проверки
```

Запуск: `go test ./pkg -run '^$' -fuzz FuzzAddPort -fuzztime 30s`.

Вывод (типичный):

### C. Термины

- **Coverage** — покрытие путей выполнения программы.

- **NLOC** — Non-comment Lines of Code (непустые строки кода без комментариев).
- **Persistent mode** — повторное использование процесса без перезапуска.
- **ASan** — AddressSanitizer; обнаруживает нарушения памяти.
- **CCN** — Cyclomatic Complexity Number (McCabe).
